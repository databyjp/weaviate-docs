Weaviate stores vector embeddings, also called "embeddings" or simply "vectors." Each element of a vector embedding is a dimension. The values are commonly stored as 32 bit floats. A single vector with 1536 dimensions uses about 6 KB of storage.

When collections have millions of objects, the total storage size for the vectors can be very large. The vectors are not just stored, they are indexed as well. This index can also grow very large. The resource costs to host the vectors and the index can be expensive.

Weaviate creates indexes to search the vector space for your collection. The default vector index is a [Hierarchical Navigable Small World (HNSW)](/weaviate/concepts/vector-index#hierarchical-navigable-small-world-hnsw-index) index. This data structure includes the vectors as well as an index graph. HNSW indexes allow fast vector searches while maintaining excellent recall, but they can be expensive to use because they are stored in RAM memory.

Updating the default index configuration settings can result in significant cost savings and even performance improvements. In many cases, you can use compression or a different index type (such as the disk-based [HFresh index](/weaviate/concepts/vector-index#hfresh-index), which keeps posting-list contents on disk and a compressed centroid index plus other metadata in memory) to change the way Weaviate stores and searches your data, and still maintain high levels of recall.

This page discusses compression algorithms. For more on indexes, see [Vector indexing](/weaviate/concepts/vector-index).

When you compress vectors, the quality of your search results depends heavily on the characteristics of the uncompressed vectors. The embedding model produces these vectors. Therefore the embedding model is key to retrieval performance of the compressed vectors. Before moving to production, experiment with different compression settings and embedding models and review the model documentation to find the combination that works best with your data set.

## Compression considerations

Before choosing a compression algorithm, consider the [underlying vector index type](#underlying-vector-index). The index type determines which compression algorithms you can use. Some compression algorithms aren't available with some index types.

The vectorizer that you use to create your object vectors may also limit your compression choices. For example, some embedding models are tuned specifically for BQ compression.

Performance and cost are also important considerations. See [Cost, recall, and speed](#cost-recall-and-speed) for details.

### Underlying vector index

This table shows the compression algorithms that are available for each index type.

| Compression type | HNSW index | Flat index | Dynamic index | HFresh index |
| :--------------- | :--------- | :--------- | :------------ | :----------- |
| PQ               | Yes        | No         | Yes           | No           |
| SQ               | Yes        | No         | Yes           | No           |
| RQ               | Yes        | Yes        | Yes           | Yes          |
| BQ               | Yes        | Yes        | Yes           | No           |

RQ comes in three bit widths, and they are not equally available. The HNSW index accepts all three: [8-bit](/weaviate/configuration/compression/rq-compression#8-bit-rq), [4-bit](/weaviate/configuration/compression/rq-compression#4-bit-rq) and [1-bit](/weaviate/configuration/compression/rq-compression#1-bit-rq). The flat index accepts 8-bit and 1-bit. The HFresh index accepts 1-bit only: RQ is mandatory on that index, so it can be neither turned off nor set to a wider bit width. A dynamic index holds a flat configuration and an HNSW configuration side by side, so each side follows its own rule: 4-bit RQ can only be set on the HNSW side, and it applies after the collection converts from flat to HNSW.

The [dynamic index](/weaviate/config-refs/indexing/vector-index.mdx#dynamic-index) is new in v1.25. This type of index is a [flat index](/weaviate/config-refs/indexing/vector-index.mdx#flat-index) until a collection reaches a threshold size. When the collection grows larger than the threshold size, the default is 10,000 objects, the collection is automatically reindexed and converted to an HNSW index.

### Cost, recall and speed

Performance includes speed and recall. In real world systems, these factors have to be balanced against cost. As you develop familiarity with your application, you can tune Weaviate to match your project and budget requirements.

#### Cost

Compression reduces the size of the vector representation used for search. This can reduce RAM requirements and infrastructure cost, especially for in-memory indexes such as HNSW, but it is not a total-memory or total-cost saving of the same proportion.

Weaviate retains uncompressed vectors for rescoring as well as the compressed index, increasing disk usage. Candidate expansion, rescoring, cache behavior, and storage I/O can change CPU and storage requirements. Compare total cost at the recall and latency your application needs, including replicas and peak headroom.

Vector-size reductions depend on the algorithm, bit width, dimensions, and encoding metadata. PQ also depends on its segment and centroid configuration. Ratios between raw float32 values and compressed codes exclude graph memory, caches, runtime state, and the retained originals.

An HNSW index comprises a connection graph as well as the vectors. Quantization methods reduce the size of the vectors, but do not affect the size of the graph. As a result, the overall memory reduction is less than the reduction in vector size and depends on the share of memory used by the graph and other structures. If you need to reduce memory further, the disk-based [HFresh index](/weaviate/concepts/vector-index#hfresh-index) avoids keeping the full graph in memory altogether.

#### Recall

Recall measures how well an algorithm finds true positive matches in a data set.

A compressed vector has less information than the corresponding uncompressed vector. An uncompressed vector that would normally match a search query might be missed if the target information is missing in the compressed vector. That missed match lowers recall.

Recall depends on the dataset and embedding model, compression algorithm and bit width, index and search settings, and rescoring. There is no fixed recall rate for a compression method. Evaluate Recall@k against ground truth for your data, including any filters used by your application.

To improve recall with compressed vectors, Weaviate over-fetches a list of candidate vectors during a search. For each item on the candidate list, Weaviate fetches the corresponding uncompressed vector. To determine the final ranking, Weaviate calculates the distances from the uncompressed vectors to the query vector.

Rescoring adds original-vector lookups and distance calculations. Its latency and I/O cost depend on the number of candidates and cache state.

Over-fetching and rescoring can improve recall by ranking retrieved candidates using original-vector distances. They cannot recover a true neighbor absent from the candidate list, so they do not guarantee the same results or recall as uncompressed search.

#### Query speed

Each compression algorithm has its own distance-computation and recall trade-offs. Faster distance calculations do not necessarily mean faster end-to-end queries at matched recall.

- PQ is configurable. The [PQ rescoring experiments](https://weaviate.io/blog/pq-rescoring#qps-vs-recall-experiments) illustrate how candidate selection and rescoring affect the speed–recall trade-off; they do not establish a universal performance ratio.

- BQ uses bitwise distance calculations, which can benefit brute-force flat search. Its quality is sensitive to the data and model. The [BQ experiments](https://weaviate.io/blog/binary-quantization/#performance-improvements-with-bq) provide examples to compare with your own workload.

- SQ uses scalar-quantized values for search. Compare it with other methods at the recall target required by your application rather than assuming a fixed speed multiplier.

- RQ uses SIMD-optimized distance computations. End-to-end performance still depends on hardware, search settings, candidate count, and rescoring. You can disable rescoring for HNSW RQ, but should measure the resulting recall as well as latency and throughput.

For a meaningful comparison, record the Weaviate version, dataset and model, distance metric, result count, index and compression settings, filters, hardware, cache state, and concurrency. Compare configurations at matched recall.

SQ and BQ both have optional vector caches. Use these configurable caches to load frequently used, uncompressed vectors into memory to improve overall search times.

#### Import speed

Importing and compressing vectors takes slightly longer than importing uncompressed vectors, but this is a one time cost. In contrast, loading a compressed index into memory is faster since there is less data to load. This means restarts are faster.

Starting in v1.22, Weaviate has an optional, [asynchronous indexing](/weaviate/config-refs/indexing/vector-index.mdx#asynchronous-indexing) feature which effectively speeds up the import process. Consider enabling asynchronous indexing to improve imports.

### Activate compression

- RQ can be enabled at creation or on an existing uncompressed HNSW index by updating its configuration. Conversion of existing vectors may run in the background; allow for conversion work before evaluating resource usage. Once RQ is enabled, its bit width and centering setting cannot be changed. For flat indexes, RQ enablement and bit width are fixed at creation. See [RQ configuration](../../configuration/compression/rq-compression.md) for index-specific instructions.

- PQ and SQ both require training data before they begin to compress data.
  - PQ's training step defines centroids for each segment.
  - SQ's training step determines the minimum and maximum values for bucket boundaries.
  - PQ and SQ both begin to compress data after you have imported a large enough training set and the training step is complete.

- Ordinary RQ requires no dataset training and can compress vectors as they are indexed. Optional centering for 4-bit HNSW RQ first estimates a mean from a per-shard training sample, so compression waits for that training step. See [RQ parameters](../../configuration/compression/rq-compression.md#rq-parameters).

- If you have async indexing and [AutoPQ enabled](/weaviate/configuration/compression/pq-compression#configure-autopq), PQ compression can be enabled anytime. If AutoPQ is not enabled, you should only enable PQ after you have imported enough objects to [train the algorithm](/weaviate/configuration/compression/pq-compression#manually-configure-pq).

- BQ doesn't require a training step.

## Recommendations

Evaluate compression when vector memory is a constraint. In [Weaviate Cloud](https://weaviate.io/pricing), applicable dimension rates can depend on compression and index type; total savings also depend on storage, replication, deployment configuration, and workload. Use a configuration-specific price estimate rather than a vector-size ratio to estimate your bill.

- For HNSW indexes, **consider 8-bit RQ compression** as a starting point. It reduces vector-code size without dataset training. Test recall, latency, and throughput with your embeddings and rescoring settings.

- If you have a small collection that uses a flat index, consider RQ compression. It reduces vector-code size; benchmark search performance against the uncompressed configuration at your required recall.

- If you have a very large data set or specialized search needs, consider PQ compression. PQ compression is very configurable, but it requires more expertise to tune well than SQ, RQ, or BQ.
